Introduction to Celonis Studio
Studio & Apps: Space, Package, and Asset!

Celonis Studio (or simply, Studio) combines the capabilities of process mining with functional expertise to offer a low-code development service. It serves as a hub for you - as analysts, app developers, and dashboard builders - to create, test, and customize dashboards, apps, and other Celonis solutions.

Business users will access the solutions you publish in the "Apps" service. Let’s take a look at Apps and what it offers your business users.

Both Apps and Studio have a very similar user interface (UI) for navigation - with Studio having additional functions that would guide you to build the Apps your business users need. Before you begin, it’s crucial to comprehend the structural elements of Studio, which dictate how Apps are housed and organized.

Check out the example of an app, with a dashboard that was built using a View in Studio.

The Knowledge Model

If you have a look at your Package, you'll notice the initial asset was created with a Knowledge Model (commonly referred as "KM"). The Knowledge Model is the semantic layer between the Data Model and assets. A Knowledge Model interacts with a Data Model, taking the data ingested from source systems to make it accessible and human-readable. The Knowledge Model stores all the reusable business definitions and knowledge on the app (Package) level.

Let’s have a look at some of the more commonly used Knowledge Model Entities.

Data
Metrics
Filters
Event Logs
Update: Knowledge Model UI

The Knowledge Model user interface (UI) has been recently updated! While the layout surfaces more features, the core functionality remains unchanged. All knowledge entities — like data/records, metrics/KPIs, and filters — function exactly as before within their connected assets.

Please note that some training may still display the previous interface. This difference should not alter the flow or content of the training.

For more information about the Knowledge Model, check out the documentation.

You'll learn more about the Knowledge Model and the uses of its specific Knowledge Entities as you learn how to build its associated assets.

So what does being the “semantic layer” technically mean? Why do assets have to be connected to a Knowledge Model? Let’s see how that happens - and more importantly, why.

Data Flow

To appreciate the Knowledge Model, you first have to understand what an app could look like.

This is an Order Management app. Notice the various types of assets in it.

In order for all these assets to have a coherent language, you’d need a central repository of all the knowledge on an app level - that’s where the Knowledge Model comes in! All the assets you see are connected to the same Knowledge Model so that a common knowledge is shared throughout.




This is how assets get data:

Data is integrated from source systems into a Data Model. The Data Model connects to a Knowledge Model in Studio — enabling data, as Knowledge Entities, to be used in assets. Data flows from the Data Model to the Knowledge Model and other assets via Process Query Language (PQL).

A note on using either case-centric or object-centric Data Models

Using the PQL Editor

Process Query Language (PQL) is a programming language used to manipulate and analyze data within the context of process mining and analytics. It is simpler than SQL and specialized for process-related queries. In the Knowledge Model (or any other asset), you’d use the PQL Editor to specify the data you want to query.

Watch the video demo to see how you’d use it in a View.




The Knowledge Sidebar in the PQL Editor surfaces all available data from the Data Model as well as all reusable business entities in the Knowledge Model. Here are a couple more pointers in the knowledge sidebar that would help you in creating PQL queries.

Search, filter, and sort
Common transformations
Inline Suggestions




Let’s now bring it all together and create a metric in the Knowledge Model. Let's say you want the total number of deliveries the company has made. You want this metric created and centralized across the app.

In the training environment, go the Knowledge Model. Create a metric using the following information:

PQL Query: COUNT("o_celonis_Delivery"."ID")

KPI name: # Deliveries

Format: Rounded Number (#,###)

Hint: To create the PQL query using the Knowledge Sidebar, you’d reference the Delivery table. Since you want to count the total number of deliveries, you can transform the (delivery) Id column using the aggregation, Count.

This is what you should see in the PQL Editor preview

[Optional] Understanding The PQL Query

Feel free to skip this page if you are already familiar with PQL or if you're planning on taking the Write PQL Queries training. This page simply explains the PQL query you've just created.




In the last exercise, you counted the number of deliveries using:

  COUNT ( "o_celonis_Delivery"."ID" )

The COUNT function aggregates the Data Model table column (i.e., Ids from the Delivery table). PQL queries require the key or ID of the data - not the display name.

"o_celonis_Delivery" is the key of the Data Model table
"ID" is the key of the Data Model table column

Put together (separated by the " . "), they inform the Celonis system that you are referencing the specific “Id” column from the "o_celonis_Delivery" Data Model table.




You should be able to see these details in the Data of the Knowledge Model.




But wait, what are keys or IDs?




The PQL function, COUNT counts the number of values in a table column. Each PQL function requires a specific expression to work - otherwise, it will express an error.

If you are unfamiliar with PQL and its functions, use the product documentation or the documentation in the PQL Editor to guide you as you create new PQL queries.

PQL is used in all Studio assets to varying degrees. That’s enough PQL for now. Let’s get back to your Package!

Permission Settings

Lastly, let’s talk about access rights. In practice, you’ll likely have various types of business users (e.g., users from the Accounts Payable, Logistics, or Customer Services departments) who will be utilizing the apps you’ve created. This means you’ll be building and publishing different types of apps to meet their specific needs. As such, it’s important to selectively grant them access to specific apps, rather than allowing all business users to access every app in the environment. This is where permission settings become crucial.

Take note that the training environment provided has a few limitations. Specifically, access to the Admin & Settings service, and Studio Permission settings have been disabled. If you have access to a productive environment, feel free to explore how these features work there.

Before we get into permissions, you first need to understand the Admin & Settings service.

In short, accessing a Celonis team typically requires an invitation and the assignment of a role. Your role defines your level of access to the services available on the Celonis platform. To access Studio, you'd need to have at either an Analyst or Admin role.

In the training environment, you have the Analyst role.

To learn more, check out the documentation or consider taking up the Set Up Security and Permissions (admin) course.

Once your business users have access to the Celonis environment (through their assigned roles), you'd want to set permissions based on the specific apps they should have access to. Permissions can be easily set based on the Studio structure levels.

Space Level
Package Level
Asset Level

Take note that not all permission options give users access to all Packages within the Space.

The 'Edit', 'Delete', and 'Manage' space options are all Space-specific permissions, which do not include access to existing Packages within the Space. If you’d like to review the details of all the Space permission options, you can refer to the documentation.

You can flexibly adjust permission settings at any level at any time. For now, simply understand that managing user permissions in Celonis has multiple layers, reflecting the necessary granularity to suit the specific circumstances of each user.

Examples of Studio Structure

When implementing Celonis, it is important to structure Studio well in order to:

improve transparency of available analyses, dashboards, and other supporting capabilities

facilitate the most optimum structure for permissions management

Scale and unify the App building experience in designated Spaces in large enterprises

Ease the browsing experience of Spaces in the Celonis platform
